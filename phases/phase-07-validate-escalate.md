   Examples that are DISPROVEN, not PROVEN, regardless of how clever the bug looks:
   - XSS / HTML injection / open redirect with no proven delivery vector (no reflected sink reachable by an attacker-controlled URL, no stored sink another user actually renders, no clickjacking/postMessage path you can actually drive).

"Attacker guesses a UUID" is not a delivery path.

   **Owned-test-account trap (mandatory for every IDOR / cross-tenant / "access victim's X" finding).** We validate with two accounts, A and B, but owning both is a TEST HARNESS, not an attacker capability. A real attacker controls only their own account and does NOT have the victim's credentials, email, session, or opaque identifiers. Such a finding has TWO independent preconditions; you must prove BOTH against the live target:
   1. **Authz broken** (the mechanic): A can reach B's resource given its identifier. Owning A+B proves this; that is what the accounts are for.
   2. **Identifier obtainable** (the delivery): an attacker who controls ONLY their own account (or nothing) can learn a victim's identifier. The v2 PoC must obtain the victim identifier from a source that does NOT require victim control: sequential / low-entropy / predictable IDs the attacker enumerates, OR the id leaking somewhere attacker-reachable (list / search / members / autocomplete / profile endpoint, JS bundle, error message, redirect, OAuth callback, public page). Reading the victim's id / email / token out of account B's own session or dashboard because we own B is NOT a delivery path and counts as ZERO evidence for #2.

   Decision rule: if the victim identifier is sequential or otherwise predictable, #2 is satisfied even if you first inferred the pattern from A's and B's own IDs (a real attacker enumerates the same range). If the identifier is a UUIDv4/v5 or other high-entropy opaque token and your search (below) finds no attacker-reachable leak, it is NOT enumerable: #2 fails and the finding is DISPROVEN regardless of how clean the authz break in #1 is. Name the missing primitive in DISPROVED.md ("victim resourceId is UUIDv4; searched X, Y, Z for a leak; none found; not enumerable"). The same rule kills any finding that simply assumes the attacker starts with the victim's email / username / password / session.
   - CSRF / clickjacking / request-forgery where the vulnerable action requires state (CSRF token, nonce, referer, custom header) that the attacker cannot actually obtain or forge cross-origin.
   - SSRF / injection bugs where the input sink is unreachable from the attacker (admin-only, internal-network-only, requires a role you cannot get) and you have no chain to reach it.
   - Auth bypasses that require a token / cookie / signed blob whose provenance you cannot explain (it just appeared in your session; you cannot show how an attacker gets one).
   - Rate-limit / account-lockout / brute-force-protection findings where the missing control is real but you never carried the brute force to an actual outcome: no valid credential / reset-OTP / 2FA code / token actually guessed, no real account compromised, no enumeration oracle run against a real population. "Endpoint never locks", "no CAPTCHA", "unlimited attempts", or "rate limit keyed on spoofable X-Forwarded-For" are HARDENING MISSES on their own. A brute force that cannot even start because no valid target exists (no enumerable admin email, no pending OTP, self-registration walled) is DISPROVEN, not Medium. The bar for PROVEN: a low-entropy secret (e.g. 4-6 digit OTP, long/no expiry) AND a demonstrated unthrottled path AND a reachable real target you can drive the guess against; then show the math and, where non-destructive, the actual successful guess. Anything short of a demonstrated compromise is DISPROVEN; do not ship the control failure alone as Medium. **Exception where the missing control IS the impact:** when the unthrottled guessing directly extracts value, the rate-limit gap is the whole finding and is PROVEN, not a hardening miss. Canonical case: gift-card / voucher / coupon / promo-code enumeration against a low-entropy code space, where unthrottled guessing returns valid codes carrying real redeemable balance. Same for any endpoint where the enumerable secret itself is the prize (redeemable token, account balance, discount code). Prove it with a real hit (non-destructively) or the demonstrated enumeration rate against the code-space size showing valid codes are reachable; escalate this fully rather than disproving it.
   - Any chain step prefixed with "assuming the attacker has X" where X is not itself proven obtainable in this report.

   Rule of thumb: if the v2 reproduction steps include "obtain victim's UUID" / "assume attacker has token" without a concrete, demonstrated, in-scope way to do that, the finding is DISPROVEN. Escalation that needs a missing primitive is not escalation, it is speculation. Mark it DISPROVEN with the missing primitive named explicitly in DISPROVED.md ("requires victim accountId, no enumeration or leak found; tried X, Y, Z").

   This applies even when the underlying technical bug is real. A real XSS sink with no delivery is still DISPROVEN for our purposes. A real IDOR on a UUID-keyed resource with no UUID leak is still DISPROVEN. We only ship findings whose full attacker path is demonstrated.

   **BUT: actively hunt for the missing primitive before concluding it does not exist.** Do not give up at "no delivery method found" without first genuinely searching. If the bug is real, the delivery vector might exist somewhere you have not looked yet. For each missing primitive, exhaust the obvious sources before downgrading:
   - **Missing victim ID (UUID, accountId, email, slug):** the source must be reachable by an attacker who controls ONLY their own account; reading it out of the victim test account does not count (owned-test-account trap above). Check every authenticated endpoint that returns lists, members, search results, autocomplete, suggestions, sharing dialogs, mentions, public profiles, sitemaps, robots.txt, JS bundles, GraphQL introspection, error messages, redirect URLs, referer leaks, OAuth callbacks, webhook payloads. Try unauthenticated enumeration. Check if ID is predictable (sequential, timestamp-based, low-entropy). If so, enumeration IS delivery. If it is UUIDv4/v5 or other high-entropy with no leak found, it is not enumerable and finding is DISPROVEN. Look at related resources attacker CAN access (their own org, shared docs, public APIs) for cross-references to victim ID.
   - **Missing XSS / HTML injection delivery:** check every place the sink's input is set: URL params (GET reflection), form fields, profile fields rendered to other users, file upload filenames, import flows (CSV/JSON), webhook bodies, email-rendered fields, OAuth state, error pages, 404 handlers, search result rendering, comment/note/mention systems, admin views that render attacker-controlled data.
   - **Missing CSRF token / nonce:** check if the token is predictable, leaked in a GET response, missing on some endpoints, accepted as empty, accepted from a different user, accepted across origins, or bypassable via XHR/fetch with a custom content-type.
   - **Missing role / admin access:** check if the role can be self-granted, granted via IDOR on a settings endpoint, bypassed by a different API version, reachable from a lower role via parameter pollution or header injection, or exposed unauthenticated on an internal endpoint.
   - **Missing token / signed blob:** check if it leaks in logs, referer, postMessage, JS bundles, third-party redirects, OAuth flows, error responses, or can be forged/replayed.

   Only after a genuine search for the delivery vector turns up nothing should the finding be DISPROVEN. Document the search in DISPROVED.md ("looked for victim accountId in: /api/users, /api/search, /api/org/members, public profile JSON, GraphQL introspection, JS bundles, sitemap, robots.txt; none returned other users' IDs"). A short search that found nothing is still better than no search.

   - **PROVEN** (the bug, at its escalated severity, reproduces with evidence, AND every precondition ledger row is `REACHABLE` against the live target): create `<finding>/v2/` and write a submission-ready report there following `{{report_format_path}}` EXACTLY. Use its platform-specific headings, classification field, Markdown rules, attachment rules, and plain-language rule. Name each account, record, data item, object, and state directly. Never use `fixture` or `fixtures` as testing shorthand in public prose. Reproduction MUST open with a runnable fastest-proof block containing actual command or exact click sequence plus matching inline screenshot, followed by a scan-friendly Prerequisites block covering accounts and how triage obtains them, tooling binaries and load-bearing flags, environment needs (VPN, IP allowlist, geo, residential egress, WAF), timing windows, side effects, and what the attacker does not need. Keep Prerequisites at 150 words maximum. Keep Business Impact, HackerOne Summary, and HackerOne Impact at 130 words maximum each. Target 500 to 1,000 words for the whole public report, with no minimum and a hard maximum of 1,500. These sections are triage summaries, not escalation logs. Write like a researcher explaining the issue, not a laboratory log: reproduction dates, exact byte counts, hashes, full identifiers, raw HTTP statuses, timing, and test history stay in reproduction output or private evidence. A concise business-scale count may remain when it changes severity; proof metadata does not. Give each fact one public home. Synthesize proven results instead of appending one paragraph per angle. Move raw evidence paths, exhaustive field lists, HTTP detail, negative-result matrices, remediation discussion, and test history to reproduction or private evidence. A screenshot beside "run steps X through Y" is not a runnable fastest proof. If your own reproduction needed a VPN, a proxy, a specific geo, or a 403 retry, that fact belongs in Prerequisites. Steps are directions only: one action each, no scale arguments or justification holding a step number, every core claim-bearing step carrying a command, every researcher-owned value carrying an explicit swap instruction, and no step pinned to perishable state without a fallback. Keep no more than six public screenshots by default. Seven to ten require genuinely multi-stage proof and a specific private gate justification; more than ten cannot pass. Move extra captures to private archive. Internal TLDR sits directly under Title with exact markers defined by selected format and exists only for internal preparation. P09 removes it before PASS. PoC snippets remain inline in numbered reproduction steps unless selected format explicitly routes an executable attachment. Reproduction must start from stated attacker capability, acquire each prerequisite in order, then invoke the vulnerable behavior. Cite or preserve evidence for both acquisition and impact.

   **Also write `<finding>/v2/report-manual.md` (mandatory for every PROVEN finding).** This is an INTERNAL, FULLY PRIVATE artifact (like `ESCALATION-LOG.md`: it lives in v2/ but is NEVER submitted and does not follow `report-format.md`). It is the exact cold-start verification and capture script for P08 and P09: every action from setup through genuine screenshot capture, with NOTHING assumed and NO unstated precondition. Later phases use it to reproduce independently and confirm each image still matches final command. Rules for it:
   - **Zero assumptions, zero unmet preconditions.** Start from a cold machine state and include literally everything: acquiring/opening the right browser profile, the exact login (real email AND real password pasted inline, copied verbatim from `sensitive/`; do NOT write "use the creds from sensitive/", paste the actual username and password), any second account/tab/OOB listener/VPS the repro needs and how to bring it up, what page to land on. If the bug needs a starting state, the steps that create that state are part of the script, not a precondition.

   - **Pick the shape that is fastest for triage, by how much state the proof carries, not by vulnerability class** (see "Choosing the proof shape" in `{{report_format_path}}`). One request with no state: inline command only. Two to four requests with no value carried between them: inline sequence, or one `fetch()` in an already-authed tab. Five or more requests, or a value carried step to step, or a loop, or an OOB listener: attach `poc.py`/`poc.sh` and still show the decisive request inline. A browser paste is usually fastest for an authenticated bug because the session rides along; a single unauthenticated command is fastest when no session is needed. Do not force a browser repro onto a finding that is naturally a terminal one, or the reverse, and do not pick terminal because it is easier to automate. Where an awkward step is unavoidable, add one clause on why (`it is httpOnly, so JavaScript cannot read it, but the DevTools Application tab can`).

   - **Every curl / DevTools-console snippet must be paste-tested verbatim**, exactly as the `report.md` rule below requires.

# Rules
- **Bounded non-destructive standard.** No deletion, lockout, denial of service, irreversible change, or spam. Non-destructive does not mean read-only or own-records-only: GET, POST, PUT, PATCH, and other state-changing requests are in bounds when they are the finding's mechanism. Prove the mechanism end-to-end on researcher-owned objects first (own account, record, domain, tenant), then confirm cross-entity reach on at most three non-owned objects with the smallest request that proves the boundary, then characterize enumerability from the identifier mechanic without bulk collection. For writes on non-owned objects prefer reversible values, restore original content where possible, and record every touched object in evidence. Program text such as "stop testing once a flaw could modify data" means stop after this bounded proof and submit; it does not forbid the proof and never requires vendor pre-authorization.
- **Account contention:** inventory all usable accounts in `sensitive/`; do not assume only A/B exist. Concurrent sub-agents may share an account for read-only validation, each in its own profile, but two concurrent sub-agents must NEVER mutate the same account at once. A finding that mutates account-level config (session lifetime, MFA, entitlements, SAML, etc.) must record the original value, restore it after proving, and run on an account no other concurrent finding is mutating. The orchestrator assigns each MUTATING sub-agent one or more specific accounts so mutating workers never collide; read-only and IDOR access is unrestricted. If more concurrent mutating findings than suitable accounts, serialize the overflow.
- **Credential findings escalate authority after liveness.** The credential-validation gate (2b) requires confirmed liveness first. After that, prove what the credential authorizes under the bounded standard: no-payload authority probes (wildcard or namespace attach/subscribe status, capability ceilings, denied-operation controls), exercise on researcher-owned objects, then at most three bounded cross-entity confirmations with lawful identifiers. Still banned: bulk or sustained cross-tenant reads, privileged actions on non-owned objects, credential reuse on other accounts.
- Proof medium: the goal is the fastest confirmation for a triager who has never seen this target. Pick by how much state the proof carries, per "Choosing the proof shape" in `{{report_format_path}}`. Chrome DevTools / UI is usually fastest for an authenticated bug because the session rides along; a single unauthenticated command is fastest when no session is needed; an attached script earns its place once the chain carries state. Showing it both ways is fine when that adds clarity. Do not force a browser repro onto a finding that is naturally a terminal one, or the reverse.
- Data-exposure proof defaults to exact values. Show up to three safe representative records, using three when available, with impact-bearing fields unmasked exactly as returned. Do not exceed three displayed records; use aggregate counts for scale. Attached script defaults to full output for same bounded sample and offers masked output only through explicit opt-in. Report exact masked-mode command and say masking happens locally. Never let masked output become only evidence for claimed leakage.
- Report must carry a runnable fastest-proof block first and a Prerequisites block second. A decisive command buried at step 3 behind setup is the most common reason a triager stalls before reaching the bug.
- Current Chrome 154 User-Agent in every command. Never copy a UA forward from an older report or existing script.
- v2 Severity is independent of v1 guess. Bugcrowd uses selected VRT priority when scored. A Bugcrowd `priority: null` leaf uses concrete proven impact with explicit rationale. HackerOne derives severity from final proven impact.
- Every payload/command referenced in v2 must exist and be copy-paste ready. No dangling references. Screenshots are captured in this phase and referenced as `![caption](screenshots/NN-name.png)`; a `![SCREENSHOT NEEDED: ...]()` placeholder is the fallback for a failed capture only, with the reason noted. P09 owns the final set and re-captures anything whose command it corrects.
- **Register every remote PoC.** Use your managed PoC endpoint documented in `$YOUR_HELPERS_ROOT/your-poc-runtime.md` for every VPS service. P07 deployments start `temporary`, expire after 24 hours unless renewed or promoted, and belong to the exact finding. Never use `nohup`, an untracked process or service, or a production mail server for new PoCs.
- **Keep required PoC infra alive; tear down throwaway artifacts.** Anything final v2 PoC depends on stays UP through P08/P09 and is declared in private `archive/POC-RUNTIME.json`. Attach source, document redeploy, and expose host override. Save server file in v2 and reference it inline. Retire intermediate deployments immediately. DISPROVEN must retire all finding PoCs. BLOCKED suspends public runtime but retains source and deployment record. Do not leave untracked listener.
- **Make DNS rebinding proof portable.** Prefer `your-rebinding-service` when its two-address, TTL-zero behavior reliably proves the sink. Report both encoded IPs, exact hostname, bounded retries, expected success signal, and cleanup. Every submit-ready rebinding report must attach a deterministic DNS server fallback with a triage-owned `REBIND_BASE` override unless another self-contained deterministic path exists. Do not force `your-rebinding-service` when caching, blocking, IPv6, CNAME, answer-order, or timing requirements make it unsuitable. Public `your-rebinding-service` plus a triage-run fallback means `POC-RUNTIME.json` uses `required:false`; stop every research-time DNS listener after evidence capture. If your managed runtime lacks UDP DNS, a final proof requiring researcher-operated live DNS is BLOCKED for P09 rather than left running manually.
- Idempotent: skip findings that already have `v2/`, skip `.dscolor` values `green`, `orange`, or `red`, and skip the entire `$YOUR_DIG_ROOT/NA-DISPROVED/` folder (everything inside it is already disproved; see step 5).
- P07 never writes green. For each Medium+ finding proven during this invocation, orchestrator changes temporary orange to blue only after confirming final `v2/report.md`. Blue is mandatory P07-to-P08 handoff state. Low and Informational are archived red and never enter P08.
- **New accounts persist to sensitive:** before dispatch, orchestrator reserves a unique unused account label for each worker allowed to register. Any account a sub-agent registers MUST be appended to `sensitive/SENSITIVE-FINDINGS*.md` immediately, with full credentials in the existing account-entry format under its reserved label. Never overwrite or rewrite existing entries.
- Never use em dashes anywhere in the reports.

# Handling BLOCKED sub-agents
A BLOCKED verdict is NOT a technical result; finding remains open. Do not retry it blindly or mark it disproven. Confirm sub-agent wrote `<finding>/v1/BLOCKED.md` with exact blocker, recovery attempts, and required resource. Record blocker in final session table, continue every other finding, then finish P07 normally. No notification is sent. A later manual run can resume after researcher supplies missing resource.

# Handling spin-off leads
When a sub-agent hands back a spin-off lead, triage it; never drop it. The default is to PURSUE worthwhile leads, not shelve them. For each lead:

1. **Filter.** Drop it only if it is out of scope (Scope section above) or a duplicate of an existing finding/report. Say which, briefly, and move on.

2. **Pressure-test the severity, then promote + dispatch.** Do NOT take the finder's severity label at face value; a sub-agent's "medium" guess is often optimistic. Challenge it first with a "so what?": what concretely does an attacker gain, is there real evidence it actually works (a confirmed response, not just a suggestive error string or a theoretical path), and does that impact genuinely reach **medium or above**?

   **SSRF kill rule (do not reframe-and-keep).** When an SSRF lead's escalation DISPROVES internal reach and there is no internal-response read, status/timing/size oracle, protocol smuggling, file read, or concrete privileged server-side request, finding is **NA, External-only** under researcher submission policy regardless of self-assigned severity. Flip it to DISPROVED and stop. Do not keep it as Medium or spend more cycles characterizing primitive. Trusted egress IP, leaked trace headers, attacker-controlled outbound OAuth credentials, full read of a public external host, external-only header injection, or hypothetical future routing do not rescue it. See `ref-ssrf-techniques.md` section "When to DROP an SSRF". A completed internal connection or oracle may remain a P07 lead for escalation, but it is not sufficient impact on its own. P09 submits SSRF only when final evidence supports High or Critical.

3. **File resource-gated leads.** If a lead is plausibly medium+ but the finder flagged that it needs something you do not have (a valid API key, a second VPS, an account type you cannot self-register, etc.), do NOT silently shelve it: append it to `$YOUR_DIG_ROOT/SPINOFF-LEADS.md` with exact required resource so researcher or a later run can resume it. Do not send a notification.

4. **File only (low value).** Leads clearly below medium (low/info with no escalation path) go to `$YOUR_DIG_ROOT/SPINOFF-LEADS.md` with what / where / why / evidence and the finding they came from, for the researcher to skim.

5. **Recursion bound.** A lead surfaced by a sub-agent that was ITSELF spawned from a spin-off lead is always just filed (no further auto-dispatch), to keep the run from ballooning. Only first-generation leads (from the original dig findings) get auto-dispatched.

For every `PROVEN` Medium, High, or Critical finding processed in this invocation, require final `v2/report.md` and private `v2/ESCALATION-LOG.md` with a substantive `## Counterevidence` section, then write blue to exact final finding folder's `.dscolor` so P08 can claim it. Return an incomplete package to its worker for correction; do not write blue on a missing or placeholder section. Never write blue for Low or Informational.

If an imported finding or dispatched spin-off resolves only to Low or Informational after its plausible Medium+ paths are disproved, stop package work. Record the technically valid primitive and evidence in `SPINOFF-LEADS.md`, write `DISPROVED.md` with reason `below_submission_floor`, synchronize honest report and folder severity, mark the folder red, and move it beneath `NA-DISPROVED/`. Do not spend time polishing screenshots or a submission report. This does not mean P07 should skip an imported Medium+ candidate before testing: it means P07 terminates it as soon as the proven ceiling falls below submission floor.

Never apply a broad colour change to skipped or pre-existing findings. Keep `BLOCKED` orange and technical disproof/no-repro/below-floor results red.
